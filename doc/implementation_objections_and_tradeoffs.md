# Android V1 实施异议与取舍记录

## 1. 不迁移原生音频引擎，只在现有播放链路上补原生媒体桥

- 原设想风险：如果把 Android V1 扩成“原生壳 + 原生音频引擎 + 后台播放服务”，会同时引入音频焦点、Service 生命周期、锁屏状态恢复和跨端播放状态同步，验证面过大。
- 当前策略：继续使用 Capacitor 轻壳和现有 Web/JS 播放链路，只在 Android 侧补一个原生媒体桥，把通知栏、锁屏和耳机键控制接到现有播放器控制器上。
- 取舍边界：V1 不保证进程被系统回收后仍继续播放，也不提供完整后台保活。
- 后续扩展：等真机路径稳定后，再把原生播放服务和保活能力单独拆成 V2 原生能力专题。

## 2. 统一弹层策略优先于逐页重做

- 原设想风险：逐页手写一套移动端 Bottom Sheet 容器，会在同一仓库里形成两套弹层体系，后续维护成本高。
- 当前策略：保持 Naive UI 体系，桌面沿用 `n-modal` / `n-dropdown`，移动端优先切到 `n-drawer`，其余弹窗由全局响应式 modal 类兜底。
- 取舍边界：P2 低频弹窗没有全部改造成独立 Bottom Sheet，只保证不超屏、可滚动、可关闭。
- 后续扩展：如果后续 Bottom Sheet 使用率继续扩大，再抽象统一的移动端弹层组件。

## 3. 播放器交互先对齐移动模型，不强行同步桌面入口

- 原设想风险：如果桌面端和移动端被强行拉成完全一致的按钮布局，会让桌面现有的操作密度和 hover 交互一起退化。
- 当前策略：移动端把播放顺序改成统一模式面板，播放队列改成底部页，底栏保留稳定的上一首/播放暂停/下一首/队列入口；桌面端保持现有随机/循环入口。
- 取舍边界：桌面端和移动端播放器入口不完全一致。
- 后续扩展：如果后续播放器整体重构，再决定是否统一桌面与移动端的播放模式入口。

## 4. 分享与外链必须收口到平台层

- 原设想风险：如果继续在业务组件里散落 `window.open`、`navigator.share`、复制链接逻辑，Capacitor 与 Web 的行为会持续分叉。
- 当前策略：用 `src/utils/platform.ts` 和 `src/utils/helper.ts` 统一分享与外链打开入口，业务层只传资源类型和 ID。
- 取舍边界：部分“复制全部信息”类功能仍保留复制行为，不强制走系统分享。
- 后续扩展：如果未来要接入分享接收、深链或埋点，可以继续在平台层扩展而不重写业务组件。

## 5. 设置页不拆移动端路由

- 原设想风险：把设置页拆成原生风格多级路由会波及现有菜单、搜索高亮、滚动定位和懒加载激活逻辑。
- 当前策略：保留当前设置信息架构，小屏下把整个设置弹窗切成全屏卡片，并通过覆盖层 + 左侧菜单抽屉维持单页流程。
- 取舍边界：设置页在手机上仍然不是原生多级导航形态。
- 后续扩展：如果后续 Android 专属设置项明显增多，再评估拆路由或拆独立页面。

## 6. 返回键统一接管，但暂不把全部页面级浮层纳入同一栈

- 原设想风险：继续依赖 Capacitor 默认返回行为会让播放器浮层、搜索态和局部抽屉互相抢返回键，直接把用户送回桌面。
- 当前策略：统一接管 Android 返回键，按“搜索态 -> 播放器动作面板/队列 -> 模态弹层 -> 全屏播放器 -> 路由返回 -> 双击回桌面”的优先级处理。
- 取舍边界：少量页面级局部 `n-drawer` 仍保留组件内局部状态，未全部接入全局关闭栈。
- 后续扩展：如果后续移动端抽屉继续增多，再抽象统一的浮层注册中心。

## 7. Last.fm 授权改成系统浏览器 + 轮询

- 原设想风险：桌面浏览器式弹窗依赖 `window.open` 和关闭状态检测，在 Capacitor 中不可用或不稳定。
- 当前策略：Capacitor 下通过系统浏览器打开授权页，同时在应用内轮询会话结果，超时后提示重试。
- 取舍边界：无法像桌面弹窗那样准确感知“用户主动关闭授权页”的时刻。
- 后续扩展：如果后续要做更完整的第三方授权体验，可以接入 deep link 或 appUrlOpen 回调。

## 8. 网络异常优先做“去打扰”，而不是把每个错误都弹出来

- 原设想风险：所有超时和网络抖动都直接走全局 warning，会在已登录状态和后台刷新场景下持续打断使用。
- 当前策略：请求层区分被动请求和主动操作，默认静默处理后台刷新、推荐刷新和搜索建议；主动操作错误按冷却时间去重。
- 取舍边界：当前主要按统一规则推断请求语义，还没给全部接口单独标注业务级错误文案。
- 后续扩展：如果后续要做更细的网络诊断，再给关键接口补显式 `meta` 和场景化错误文案。

## 9. 首页与歌词页只做兜底，不做大改版

- 原设想风险：首页卡片流和歌词页一旦做结构性改版，会牵动大量现有交互与动画，不符合 V1 的风险预算。
- 当前策略：先补全全局安全区、底部播放器留白、弹层切换和横向溢出约束，让现有页面在手机上可用。
- 取舍边界：首页和歌词页仍保留现有信息架构，视觉层没有进行 Android 专属重设计。
- 后续扩展：等 P0 路径稳定后，再按真实使用反馈决定是否做视觉重排。

## 10. 生成产物不删，只从 lint 中隔离

- 原设想风险：每次 `cap:sync` 后再手动清理 Android 复制出的前端产物，容易误删、漏删，也会增加验收链不确定性。
- 当前策略：在 ESLint 层忽略 `dist_mobile` 和 Android 同步产物，只让 lint 覆盖真实源码。
- 取舍边界：工作树中仍然会出现同步产物变更。
- 后续扩展：如果后续 CI 需要更干净的工作树，可以再补专门的同步/清理流程，但不应影响源码质量检查。

## 11. Android 播放解锁允许直连网易云回退源

- 原设想风险：移动端完全依赖自建服务器同时提供 `/api/netease` 和 `/api/unblock`，一旦只部署了前者，很多版权受限歌曲会直接拿不到播放源。
- 当前策略：Android 与其他非 Electron 场景保留原有解锁链路，但当配置的 `/api/unblock/netease` 不可用时，允许回退到 Electron 端同源方案所使用的公共网易云解锁服务。
- 取舍边界：当前只对网易云解锁源补了直连回退，`Bodian / Gequbao / Kuwo` 仍优先依赖服务端 `/api/unblock`。
- 后续扩展：如果后续要把其他解锁源也下放到移动端，需要单独评估其跨域、签名与可维护性，不宜在 V1 里一并扩张。

## 12. 息屏连续播放先靠 `WAKE_LOCK` 与播放器自恢复兜底

- 原设想风险：如果直接把 Android 版本扩成前台播放服务或原生音频引擎，虽然能更彻底解决息屏问题，但会把 V1 重新推回高风险原生改造。
- 当前策略：继续保留 Web/JS 播放链路，只在 Android 原生媒体桥里持有 `PARTIAL_WAKE_LOCK`，并在应用进入 `pause / background / resume` 生命周期时对仍应保持播放的会话做一次恢复兜底。
- 取舍边界：当前目标是修复“自然黑屏后马上暂停”这一类息屏中断，不承诺被系统彻底杀进程后的连续播放。
- 后续扩展：如果后续仍有机型在深度省电模式下中断播放，再评估是否需要前台服务或原生播放服务。
